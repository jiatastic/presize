presizeBuild-time image optimization for Next.js and static sites

v0.1.0 on npm · Node.js 20.9 or later · MIT

one command, at build time
$ npx presize images --out public/img --display 400 --target

target 80very high quality, for most sites. Click 80 to change it.

Image optimization that looks at each image before deciding how hard to compress it.

presize turns a folder of images into AVIF and WebP files at the widths you actually show them, and writes a small manifest with srcset data and a blurred placeholder for each one. It runs once, at build time. You serve the files from any static host, with no image server and no per-image bill.

Most tools give every image the same quality setting. presize scores each encode with SSIMULACRA2, a measure of how different two images look to a person, and keeps the smallest file that reaches the score you ask for. A flat logo gets a low setting, a busy photograph a high one, and both end up looking the same amount of right.

Start

$ npm install -D presize

The command at the top, run on a folder of 22 images, prints:

widths 400, 800 · avif + webp · target score 80
22 images, 2.3 MiB as sources
  avif  400w 250 KiB  800w 563 KiB  · median q62, score 80.4
  webp  400w 345 KiB  800w 928 KiB  · median q84, score 80.4
22 made, 0 unchanged, 0 failed · 29.2s

--display 400 is the width the images appear at on the page; presize makes files for normal and 2× screens. --target 80 is the score every file must reach. Run it again and only new or changed images are encoded.

Then build a <picture> from the manifest, wherever your pages render:

import { picture } from "presize/manifest";
import data from "./public/img/presize.json";

picture(data.images["hero.jpg"], { alt: "", sizes: "400px" });

presize/manifest has no dependencies, so the encoder never loads where your site runs. There are examples for Next.js, Astro and plain Node.

Next.js

Wrap your config, and next/image serves presized WebP from public/. Nothing is resized when a page is requested, so there's no Vercel image optimization quota or bill, and it works with output: "export".

// next.config.ts
import { withPresize } from "presize/next";

export default withPresize({ /* your config */ });

next build encodes public/ into public/_presize, only new or changed images, and each width next/image asks for gets the smallest copy at least that wide. Copies are cached for a year, since their names carry a content hash. In CI the output is kept in .next/cache. Static imports and remote URLs load as they are; for AVIF, use presize/manifest and a <picture>.

Choosing a target

90
Visually lossless at a normal distance. Photography, hero images.
80
Very high quality. Most sites.
70
High quality; you'd see artifacts if you looked for them. Thumbnails, dense grids.

Benchmark

155 real email images at 640 pixels wide: product photos, banners and logos. To get every image to the same score with one setting, you have to pick the setting the hardest image needs. presize gives each image only what it needs.

The fixed setting is the lowest that brings 95% of images to the score; presize brings all of them. The search costs about 1.4 s per AVIF and 0.7 s per WebP on one laptop core, once per image.

How it works

For each width, presize resizes the image once and keeps those pixels as the reference. It then finds the lowest quality that reaches the target by bisection, about seven encodes, each scored against the reference, so the score judges the compression and not the resize. Transparent images are scored over white and over black, and the worse score counts.

Encoding is done by sharp. SSIMULACRA2 is plain TypeScript, ported from the rust-av crate; on the crate's reference pair the two scores differ by 0.0002.

When not to use it

Images that only exist at runtime, like uploads or remote URLs, need an on-request optimizer such as imgproxy or your CDN's image service. presize is for the images you have when you build.

Questions

How is presize different from sharp?

sharp is the encoder; presize uses it. presize decides what to encode: the widths you display, and for each image and width the lowest quality whose SSIMULACRA2 score reaches your target. It also writes a manifest with srcset data and a ThumbHash placeholder, and skips images that haven't changed.

How is it different from Vercel Image Optimization and the default next/image loader?

Those resize images when they are first requested, on a server, with a monthly quota or a per-image bill. presize makes the files once during next build and next/image serves them as static files, so there is nothing to bill or run out of, and it works with output: "export".

How is it different from imagemin, vite-imagetools or next-image-export-optimizer?

They encode every image at one quality setting. presize measures each encode and keeps the smallest file that reaches the score you ask for. On the 155 images above that took 22–41% fewer bytes than the one setting that brings 95% of them to the same score.

Does it support AVIF?

Yes. The CLI and API write AVIF and WebP, and presize/manifest builds a <picture> with an AVIF source. The Next.js loader serves WebP only, because a loader returns one URL per width.

How long does it take?

About 1.4 s per AVIF and 0.7 s per WebP on one laptop core, once per image and width. Later runs only encode new or changed images, and in CI the Next.js integration keeps its output in .next/cache.

Where can I host the images?

Anywhere that serves static files: Vercel, Netlify, Cloudflare Pages, GitHub Pages, S3 or your own server. No image server is needed.
